# 13 - SDLC, Release, Promotion and Rollback

This is the delivery contract for the platform. Everything here is implemented
in this repo — no theory.

## Gap analysis (what was missing before this change)

| Gap | Fixed by |
| --- | --- |
| No branching model, no protected branch | Trunk-based + `scripts/setup-branch-protection.sh`, `.github/CODEOWNERS`, PR template |
| No semantic versioning, no Git tags, no GitHub Releases | `.github/workflows/release.yaml` (tag `v*`) |
| Images and charts versioned only by commit SHA | Release promotes immutable ECR images at the same semver; Helm charts remain Git-sourced |
| No promotion path — every environment rebuilt its own image | `.github/workflows/promote.yaml`, values-only, order-enforced |
| No record of what runs where | `environments/<env>/version.yaml`, `releases/<version>.yaml` |
| No rollback procedure | `scripts/rollback.sh` (Git-first, so self-heal cannot fight it) |
| No approvals before production | GitHub Environment `production` with required reviewers |
| No node scaling | `infrastructure/modules/addons/cluster-autoscaler.tf` (IRSA + auto-discovery) |
| Tag mutability risk | Production ECR is `IMMUTABLE`; release tags protected by a repo ruleset |

## SDLC

```text
feature/*  ->  PR  ->  app-ci (test, Sonar, Dependency-Check, Trivy)  ->  review
   ->  merge to main  ->  app-ci builds + pushes <sha>  ->  auto-deploy DEV
   ->  git tag v2.0.1 ->  release.yaml: promote ECR image artifacts + GitHub Release
   ->  promote QA  ->  promote STAGING  ->  promote PRODUCTION (approval)
```

Stages, in one line each:

1. **Feature branch** — short-lived, branched from `main`.
2. **PR** — `app-ci` runs unit tests, SonarQube, OWASP Dependency-Check, image
   build and Trivy. Nothing is pushed to ECR from a PR.
3. **Review** — CODEOWNERS approval, required status checks, linear history.
4. **Merge** — squash to `main`; `main` is always releasable.
5. **Build** — image built once, tagged with the commit SHA and pushed to ECR.
6. **GitOps write-back** — `charts/<svc>/values-dev.yaml` gets the SHA tag.
7. **ArgoCD** — auto-sync, self-heal, prune deploy it to `roboshop-dev`.
8. **Release** — a Git tag freezes that commit as a semantic version.
9. **Promotion** — QA, staging, production receive that exact artifact.

## Git strategy: trunk-based (not GitFlow)

One long-lived branch (`main`) plus short-lived `feature/*`, `bugfix/*`,
`hotfix/*`. `release/*` is used only when production must be patched while
`main` has already moved on.

Why not GitFlow: GitFlow's `develop` branch exists to batch releases for
infrequent, manual shipping. With ArgoCD auto-syncing `main` into dev and a tag
freezing any commit into a release, `develop` adds a merge queue and a
permanent divergence for zero benefit. A small team ships several times a day —
trunk-based is what actually matches that. Environment state lives in values
files, not in branches; branches per environment are the classic GitOps
anti-pattern (drift, cherry-pick hell, "which branch is prod?").

Branch → pipeline mapping:

| Branch / ref | Runs | Deploys |
| --- | --- | --- |
| `feature/*`, `bugfix/*` (PR) | app-ci, helm-ci, terraform plan | nothing |
| `main` | app-ci build + push, GitOps write-back | dev |
| tag `v*` | release.yaml | nothing (creates artifacts) |
| manual dispatch | promote.yaml | qa / staging / production |
| nightly | dast-zap.yaml | nothing |

## Release strategy

- **SemVer** — `MAJOR.MINOR.PATCH`; the Git tag `v2.0.1` is the trigger.
- **Image version** — `roboshop/<svc>:2.0.1`, created by an ECR manifest copy
  from `:<sha>`. No rebuild, so the bytes cannot drift.
- **Chart version** — chart `version` and `appVersion` both set to `2.0.1`,
  kept in Git and consumed directly by Argo CD from `charts/<chart>`.
- **Release notes** — generated by GitHub from merged PRs.
- **`latest` is never used** anywhere; production ECR repos are `IMMUTABLE`.
- **Digest pinning** — promotion writes `image.digest` alongside the tag, and
  `charts/common` renders `repo@sha256:...` when a digest is present.

## Promotion

`promote.yaml` refuses to promote a version to an environment unless the
previous environment already runs it (`environments/<prev>/version.yaml`).
Production is gated by a GitHub Environment approval. The job only edits
`charts/*/values-<env>.yaml` and `environments/<env>/version.yaml`, commits, and
lets ArgoCD do the deployment.

```bash
gh workflow run promote.yaml -f version=2.0.1 -f environment=qa
gh workflow run promote.yaml -f version=2.0.1 -f environment=production
```

## Deployment strategy: rolling update

Implemented in `charts/common/templates/_deployment.tpl`
(`maxUnavailable: 0`, `maxSurge: 1`) with readiness probes and PDBs.

Why rolling and not blue/green or canary: these are stateless HTTP services
behind one ALB, with backwards-compatible schema changes. Rolling gives
zero-downtime deploys with no duplicate infrastructure cost, no traffic-splitting
controller (Argo Rollouts / Flagger / a service mesh) and no second copy of the
datastores. Blue/green doubles cluster cost for a few minutes of confidence;
canary needs per-service SLO metrics and an automated analysis loop that a
small team will not maintain. Staging plus a fast, boring rollback beats both.

Rollback is a Git operation:

```bash
./scripts/rollback.sh production 2.0.0
git commit -am 'fix(rollback): production -> 2.0.0' && git push
```

Never `kubectl rollout undo` on its own — ArgoCD self-heal reverts it within a
sync interval. Fix Git; the cluster follows.

## Logging: Fluent Bit → OpenSearch (not ELK)

Same collector either way. OpenSearch is chosen because it is Apache-2.0 with no
license trap, runs as a 3-node StatefulSet on the same EKS cluster, and has a
managed AWS fallback (Amazon OpenSearch Service) if self-hosting stops being
worth it. Elastic's SSPL relicensing plus Logstash's JVM footprint buys nothing
here — Fluent Bit already does parsing and enrichment at ~30 MB per node.
Retention is enforced by the ISM policy in `logging/opensearch/ism-policy.json`.

## Interview answer, condensed

> We build an image exactly once, on merge to `main`, tagged with the commit
> SHA. A Git tag turns that commit into a semantic version by re-tagging the
> ECR image promotion with Git-sourced Helm charts — no rebuild,
> so what QA signed off on is what production runs. Promotion is a values-only
> commit gated on the previous environment plus a GitHub approval for prod;
> ArgoCD syncs it. Rollback is the same workflow pointed at the previous
> version, because if you roll back in the cluster instead of in Git, self-heal
> puts the bad version straight back.
